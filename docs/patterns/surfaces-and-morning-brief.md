# Pattern: surfaces and the morning brief

Status: draft
Owner: maintainers of this template package

## Problem

An OS that does real work produces a great deal of state: intents, packages, cells, attempts,
evidence, routes, budgets, drafts, holds, decisions, work items, audit events. Put all of it in front
of a Director and they stop looking. Hide all of it from the Lead who runs the factories and they
cannot steer. And if acting on any item means leaving the OS to open mail, a document library or a
board, the OS has added a step instead of removing one.

## The pattern

### Two shapes of console, one contract

A **calm, decision-centric** console serves people whose job is to decide. It is one column, read
top to bottom in the order a decision is made: the morning brief, the decisions queue, drafts awaiting
review rendered inline, work items, program rollups, today's calendar, threads needing a reply. Each
panel shows at most seven items. There are no logs, no model text, no route names, no cell internals.
Those exist one drill-down away, hidden on purpose: a Director decides on outcomes and risks, not
mechanisms.

A **dense** console serves people who steer the machinery: intents with their journey stage, SE
packages with council state, factory cells with fence, attempt and verifier result, the evidence tail,
routes and budgets, batch windows, the audit tail, holds and the kill switch. It is filterable and
keyboard-driven.

A **generic** console sits between them and is the default until a profile defines the other two.

Both read the same state through the same read models and perform the same write actions, documented
per console in `CONSOLE_API_CONTRACT.md`. Every write names its CLI command, whether it is a protected
effect, the decision record it must produce and the audit event it writes.

### The console acts; the Principal never leaves

`externalToolsHidden` is on by default. Approving a draft sends it, as a protected effect bound to a
decision on the exact payload. Approving a work item projects it onto the board that needs it, and the
console says so before the click: "this will appear on the Director's board and stay current".
Releasing a hold is one button backed by a decision record. The Principal is never told to go and do
the last step somewhere else.

### The morning brief is the daily contract

Every Principal with a Chief of Staff gets a brief at a configured time, through configured channels
(the console and a Markdown file by default; an email or chat *draft to themself* if they want it),
with a reading-time budget and an item cap. Sections come in the configured order from a fixed
vocabulary: overnight completed, decisions needed, drafts awaiting review, holds, failures and parked,
program rollup, today's calendar, threads needing reply, budget and resources, risks and escalations,
what the OS will do today.

The brief is calm by construction:

- decisions first, whatever the section order;
- one line per item: title, why it matters, the one action;
- references, never payloads;
- nothing claimed that has no record;
- overflow becomes "N more in the console";
- an empty section disappears, except "no decisions needed today", so silence is never ambiguous.

Each item's action maps to a console button and a CLI command. A decision item also says what
approval causes, for a work item typically "appears on <board> and stays current". The brief is
compiled from state (`aof brief build`), not written by a model from memory, so it can only cite ids
that exist.

A Director's brief leans on decisions, drafts, rollups and the calendar. A Lead's leans on overnight
candidates, failures, cells and budget. The same format serves both because the sections are
configuration.

### The engineering surface is agent-agnostic

Coding agents change faster than organizations. The engineering surface depends on a contract, not a
product: `lane-prompt-in-candidate-and-evidence-out`. The OS gives an agent a lane prompt, a repository
context pack, the verification catalogue, a tool allowlist, a data tier and a deadline. The agent
returns a candidate branch or bundle, evidence records, a review-ready summary and an explicit list of
what it did not verify. The OS then runs its own reviewer and verifier. The adapter is MCP (the OS
serves its tools through `aof mcp-serve`), CLI, API or file-drop. Swapping agents is one config key
followed by a re-run of the wave-1 first task and an evidence comparison.

### A delivery ladder, not a big bang

At PoC the console is static HTML generated by `aof console build`, with each button showing the
exact CLI command. At MVP the same contract is served by a loopback-only local web app whose buttons
perform the actions. A desktop shell is optional later. State formats and action semantics never
change between rungs, so nothing built at PoC is thrown away.

## Rules

1. Every Principal has exactly one place to act: their console (or, before one exists, the brief plus CLI).
2. A calm console shows at most seven items per panel and no logs, model text or mechanism detail by default.
3. Decisions come first in every brief and every calm console.
4. Every item carries one action, and every action maps to a CLI command and a console button.
5. The console performs actions through the OS; it never talks to an integration itself.
6. Every write produces its decision record where required and its audit event, or it is refused.
7. A decision binds to the digest of the briefing shown; a stale briefing is re-briefed, not approved.
8. The brief is compiled from state and cites only ids that exist at compile time.
9. Coding agents are swapped by configuration and judged by evidence, never by reputation.
10. Move up the delivery ladder only when the lower rung is in daily use; keep the contract unchanged.

## Anti-patterns

- **The dashboard of everything.** A single dense screen for everyone serves no one; Directors stop opening it.
- **Deep links out.** "Click here to open the draft in your mail client" moves the work back to the Principal.
- **Model-written briefs.** A brief generated from memory invents status. Compile it from records.
- **Agent lock-in.** Prompts, tools and evidence formats tied to one coding agent make the next swap a rewrite.
- **Notification spam.** Interrupting during quiet hours for anything but a kill switch or a boundary breach
  trains people to ignore the OS.
